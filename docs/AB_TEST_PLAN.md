# План A/B теста для сравнения моделей дефолта

## Что именно сравниваем
Берём два алгоритма на одних и тех же признаках, входной JSON у обоих одинаковый:
v1 (контроль): pipeline StandardScaler + LogisticRegression models/model_v1.joblib
v2 (тест): RandomForestClassifier models/model_v2.joblib

## Разделение трафика
### Реализация в API
В текущей версии выбирается явно полем JSON, POST /predict принимает опциональный ключ "model_version": "v1" и "v2" и если ключ не передан, используется дефолт v1

### Как бы концептуально сделали в продакшене
В реальном проде можно было бы назначить группу через хэш от application_id, это важно, потому что один и тот же клиент всегда попадает в одну группу. Если назначать случайно при каждом запросе, один клиент может получить разные решения по одной заявке, и это уже не A/B, а шум. model_version клиенту не передаётся, версию(метаданные модели) сервер пишет в лог

## Длительность теста
2-4 недели чтобы захватить недельную сезонность в поведении клиентов

## Минимальный размер выборки
Не менее 5000 наблюдений в каждой группе. В нашем датасете доля дефолтов около 22%, это baseline. При таком балансе 5000 наблюдений дают погрешность примерно 1-2 п.п. на 95% ДИ достаточно, чтобы увидеть реальную разницу между моделями, а не шум. Чтобы еще повысить точность можно посчитать через power analysis с ожидаемым эффектом

## Метрики
Основная: F1-score для класса дефолта, тк она штрафует и за пропущенных должников, и за лишние отказы
Дополнительная: Precision для класса дефолта, в кредитном скоринге важно контролировать ложные тревоги, то есть ошибочно считаем плохим хорошего клиента, бьем по выручке и конверсии

## Статистический анализ
F1 и Precision сравниваю через z-test для пропорций где выборки большие, нормальное приближение работает. Для денежных метрик типа Expected Loss распределение скорее всего скошенное, поэтому t-test может не подойти, там bootstrap надёжнее, доверительные интервалы везде 95%.

## Критерий успеха
v2 считается успешной, если одновременно:
1. F1(v2) > F1(v1) и разница статистически значима при которой p-value < 0.05
2. Precision(v2) не хуже Precision(v1) или улучшается
3. ключевая бизнес-метрика (ожидаемые потери / доля одобрений при фиксированном риске) не ухудшается
Улучшить F1 можно просто снизив порог предсказания, тогда модель будет находить больше должников но и отказывать больше нормальным клиентам. Поэтому одного F1 недостаточно, нужно чтобы Precision не проседал ниже v1. А третье условие про бизнес метрику страхует от ситуации когда метрики выросли, а банк при этом теряет больше денег или одобряет меньше заявок.

## Бизнес-метрики для заказчика
Обе метрики считаются прямо из default_probability в ответе API дополнительных данных не нужно.
Expected Loss: берём default_probability как PD_i, умножаем на сумму кредита и условную долю потерь, LGD, обычно фиксируют на уровне 0.45 для необеспеченных кредитов. Суммируем по портфелю, модель с более точным PD_i даёт более реалистичную оценку банк резервирует ровно столько сколько нужно, а не с запасом.
Доля одобрений: фиксируем целевой уровень дефолтов в портфеле, например 5%. Смотрим сколько заявок можно одобрить при пороге default_probability < X так чтобы ожидаемый дефолт не превысил 5%. У более точной модели этот X будет выше значит одобрим больше клиентов при том же риске.
